# 无框线电子对账单：需求与验收

日期：2026-09-14

## 工作方式与依据

按需求、验收条件、方案、实现、验证、复核的顺序推进。用户提供的上下文整理作为问题线索，代码与原件用于核实；旧文档中的提交、推送授权不作为本次发布指令。

## 本轮需求

1. 在原有批量 PDF → 核对 → Excel 流程中，增加按表头和文字坐标识别的通用读取方式，不增加银行专用适配器。
2. 支持无画线、紧邻列、跨页重复表头、跨行摘要/对手名称、借贷分列与明确标注借贷合一的金额列；合一金额以负数为借方、正数为贷方。不能把模糊的“金额”列擅自当作有符号金额。
3. 必填核心为日期、金额及余额。原件没有流水号列时保留空值，票据号仍在票据号列，不伪造银行流水号。原件有流水号列却漏读的情况仍失败。
4. 缺少声明笔数/借贷合计时，默认采用证据核对：只有所有页的交易区域被识别、无未识别行，且连续余额、原件期初期末、首末笔检查全通过，才可替代缺失项目。已有声明数不相符必须失败。零交易不能只凭余额相等宣告通过。
5. 对未取得的声明项目和流水号明确提示，并在 Excel 列出核对依据。缺少独立期初或期末、页遗漏、金额/日期异常均不能通过。余额一致不代表已经完成不存在的笔数/合计核对。
6. 原件的首张“上页余额”可作期初；后页上页余额只作跨页核对。明确账期及货币应进入期间衔接检查。
7. 界面显示当前读取方式、视觉模型页码、已用时间，首份也应写日志。保留强制视觉模式的原有语义，启动时明确说明当前模式。

## 验收条件

- 七份本地样本以关闭模型的批处理完成，逐份报告页数、笔数、方式、耗时、核对结果和期间衔接结果；不在仓库放客户明细。
- 生成的无框线测试 PDF 覆盖不同表头、借贷分列、缺流水号、换行、跨页、贴邻金额/户名；核对预设明细与实际明细。
- 故意漏行、坏金额、坏日期、页缺表头、缺控制余额、错误声明合计、余额链断裂时拒绝通过；相同日期/相同金额交易不自动去重。
- 原有银行读取、强制模型、断点续传、排序、导出回归通过。模型进度测试用模拟响应，无需传出客户资料。
- Excel 可回读，声明缺失仍为空，提示和依据可见，失败交易进入待核查表。

## 边界

本轮不承诺覆盖所有银行或所有版式，不新增 OCR、并发模型请求、自动删除原件、修改用户保存配置或远程发布。无法可靠识别的格式保留失败原因并继续原有兜底。
